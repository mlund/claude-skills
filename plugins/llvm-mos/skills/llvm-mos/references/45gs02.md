## 1. What's supported

The assembler implements the **full 45GS02 instruction set**, including the 65CE02/4510 base and every 45GS02 extension. Verified as assembling on `-mcpu=mos45gs02`:

- **Q (32-bit) ops**: `LDQ STQ ADCQ SBCQ ANDQ ORQ EORQ ASLQ ASRQ LSRQ ROLQ RORQ INQ DEQ CPQ`(=`CMPQ`)` BITQ`
- **Z register**: `LDZ TAZ TZA INZ DEZ CPZ PHZ PLZ`
- **65CE02/4510**: `BSR PHW RTN NEG INW DEW ASW ROW TAB TBA`, stack-relative `(d,SP),Y`. `PHW` takes both immediate and absolute (`phw #$eaea` → `f4`, `phw $eaea` → `fc`)
- **Memory mapping**: `MAP`, `EOM`
- **32-bit indirect**: `[$nn],Z` for both byte and quad operations

Mnemonics that look like they belong but **don't assemble** on `-mcpu=mos45gs02`:

| Mnemonic | Error | Why |
|---|---|---|
| `RESQ`, `RSVQ` | `invalid instruction` | Not implemented in any operand form; absent from the upstream opcode test |
| `PHD` | `instruction requires a CPU feature not currently enabled` | 65816 (push direct-page register), not 65CE02 — use `PHW` to push a word |

The authoritative lists are the upstream assembler tests in the compiler repo ([llvm-mos](https://github.com/llvm-mos/llvm-mos)), under `llvm/test/MC/MOS/`. They're the fastest way to settle any "does this mnemonic exist" question:

```
llvm/test/MC/MOS/all-45gs02-opcodes.s     # Q ops, [$nn],z
llvm/test/MC/MOS/all-65ce02-opcodes.s     # BSR/PHW/RTN/TAB/TBA/PHZ
llvm/test/MC/MOS/all-4510-opcodes.s       # MAP ($5c), EOM ($ea)
```

Each line carries its expected encoding as a `; CHECK:` comment, so they double as an encoding reference. There is one per CPU (`all-6502-`, `all-65c02-`, `all-huc6280-`, …). Failing that, assembling a one-line probe with `mos-clang -c -mcpu=mos45gs02` settles it locally.

So writing 45GS02 assembly — in `.s` files or inline — works without restriction. The one real gap is on the **C side**: there are no `z` or `q` inline-asm constraints (all four spellings `z`/`Z`/`q`/`Q` are rejected with `invalid input constraint`), so values move in and out of Z and Q through A/X/Y or memory. §7 covers the patterns.

## 2. The Z=0 invariant — read this first

**Z must be zero whenever control is in compiled code.** Your assembly may use Z freely — that's the whole point of `ldz #$01` / `lda [$12],z` — it just has to put it back before compiled code runs again. Compiled code never sets Z, never checks it, and has no representation of it; it simply assumes Z=0 on every instruction it executes.

The useful precision is in *which* moments count as "compiled code runs again", because it is more than just returning:

- Returning from an inline asm block
- Returning from an external `.s` routine
- Returning from an interrupt handler
- **Calling into C from your own assembly** — the one people miss, because it happens mid-routine rather than at the end

Between those points, Z is yours. Leaving it non-zero across any of them silently corrupts memory access across the entire program.

**The compiler gives you nothing here — this is entirely manual.** Verified against clang 22:

| | |
|---|---|
| Input/output constraint | None. `z`, `Z`, `q`, `Q` → `error: invalid input constraint` |
| Clobber list entry | None. `::: "z"` → `error: unknown register name 'z' in asm` |
| Automatic save/restore | None, in any construct, including `__attribute__((interrupt))` |
| Startup initialization | None — the SDK contains no `ldz` at all; Z=0 is inherited from entry and assumed forever after |
| Diagnostic when violated | None |

Because Z can't even be *named* in a clobber list, there is no way to tell the compiler you touched it. `ldz #0` written by hand is the only mechanism that exists.

The reason is in the encoding, not in a convention. On the 4510/45GS02 the "plain" base-page indirect mode *is* Z-indexed — these assemble to the identical opcode:

```
       0: 92 12    sta ($12),z
       2: 92 12    sta ($12),z     ; written as  sta ($12)
```

Both `sta ($12)` and `sta ($12),z` are `$92`. The compiler emits `lda (__rcN)` / `sta (__rcN)` constantly for pointer dereferences, and every one of them is really `(__rcN),Z`. With Z=3, every such access is offset by three bytes.

The asm listing actively hides this — the source form has no `,z` in it, and only the disassembler shows what the opcode really is:

```
compiler emits:      lda (__rc2)          sta (__rc20)
disassembles as:     b2 00  lda ($0),z    92 00  sta ($0),z
```

The failure mode is nasty: no crash at the point of the bug, no diagnostic, just wrong data somewhere else entirely, dependent on which pointer accesses happen to run next. Treat `LDZ #0` as part of the exit sequence of anything that touches Z.

Note there is no precedent to copy from: the SDK contains no `ldz`/`taz`/`tza` anywhere, because nothing in it ever disturbs Z. You are the first code in the program to touch it, and nothing downstream will repair it.

**In inline asm** — restore before the block ends:

```c
asm volatile("ldz #$01\n\t"
             "sta [$12],z\n\t"
             "ldz #0"          // mandatory
             :: "a"(v) : "p");
```

**In an external `.s` function** — restore before `RTS`, alongside the callee-saved registers:

```asm
.global far_poke
far_poke:
    ldz #$01
    sta [$12],z
    ldz #0            ; part of the return sequence, not optional
    rts
```

**In an interrupt handler** — restore before `RTI`, since the interrupted code is entitled to Z=0 just as much as a caller is. `__attribute__((interrupt))` saves and restores A/X/Y for you but does not manage Z; if your handler touches it, that's yours to fix.

**Calling *into* C from your own assembly** — the easy one to miss, and the reason "restore before you return" is an incomplete rule rather than a wrong one. Z must already be 0 at the `jsr`, not merely by the time you get back:

```asm
    ldz #$01
    lda [$12],z
    ldz #0            ; BEFORE the call, not after it
    jsr process_byte  ; compiled C — dereferences pointers, assumes Z=0
    rts
```

So Z *is* a register you may borrow and give back — the discipline is just that the loan has to end before compiled code next runs, which may be sooner than your `rts`. Narrowing the borrow to the few instructions that actually need it, and writing `ldz #0` immediately after them rather than at the end of the routine, makes the rule hard to get wrong.

## 3. The register file

| Register | Width | Notes |
|---|---|---|
| A, X, Y | 8 | As always |
| Z | 8 | Fourth index register. **Must be 0 in compiled code** (§2) |
| B | 8 | Base page: relocates the "zero page" to any 256-byte window via `TAB`/`TBA` |
| SP | 16 | Stack can leave page 1; stack-relative addressing `(d,SP),Y` |
| Q | 32 | Pseudo-register: A=LSB, X, Y, Z=MSB |
| MAP | — | Memory mapping state, set by the `MAP` instruction |

**Don't relocate B under compiled code.** llvm-mos places the imaginary registers at fixed zero-page addresses chosen by the linker script; changing the base page moves them out from under the compiler. If you use `TAB`, restore it before returning, on the same discipline as Z.

## 4. The Q pseudo-register

Q is A, X, Y, and Z acting as one 32-bit register — **A holds the least significant byte, Z the most significant**. Writing A changes Q's low byte and vice versa; they are the same silicon.

Q instructions are encoded by prefixing the ordinary opcode with `$42 $42` (two `NEG`s, a sequence that can't occur meaningfully otherwise). You can see it in the disassembly:

```
   42 42 85 12       stq $12          ; base-page quad
   42 42 8d 34 12    stq $1234        ; absolute quad
   42 42 92 12       stq ($12)        ; base-page indirect quad
   42 42 ea 92 12    stq [$12]        ; 32-bit indirect quad ($ea = NOP prefix)
```

The prefix costs cycles — the CPU skips over the prefix bytes — so Q ops are not free, but they beat four separate byte operations for bulk moves and 32-bit arithmetic.

**Addressing modes, verified by assembling each one.** Load and store are *not* symmetric — the indirect forms differ, which is the easiest thing to get wrong:

| Mode | `LDQ` | `STQ` | `CPQ`/`CMPQ` |
|---|---|---|---|
| base page `$nn` | OK | OK | OK |
| absolute `$nnnn` | OK | OK | OK |
| indirect `($nn)` | **no** | OK | OK |
| indirect indexed `($nn),z` | OK | **no** | **no** |
| 32-bit `[$nn]` | **no** | OK | OK |
| 32-bit indexed `[$nn],z` | OK | **no** | **no** |

**`LDQ` is the only Q instruction that takes `,z`; every other one uses the bare indirect.** This follows from Z being *part of* Q — anything but a load would need Z as both index and data — and matches the MEGA65 Book, where only `LDQ` adds Z. Confirmed against the upstream assembler test `llvm/test/MC/MOS/all-45gs02-opcodes.s`.

`CPQ` and `CMPQ` are aliases — identical encodings (`cpq $12` and `cmpq $12` both give `42 42 c5 12`). The upstream test uses `CPQ`.

Errors you'll get:

- `stq ($nn),z`, `stq [$nn],z` — `invalid operand for instruction`.
- `ldq ($nn)`, `ldq [$nn]` — `operand must be a 16-bit address`. Confusingly, `ldq ($nnnn)` reports the *opposite*, `operand must be an 8-bit address`: there is no bare-indirect `LDQ` in any operand width, and the two candidate encodings each blame the other. Write `ldq ($nn),z` with Z=0 when you want a plain indirect load.
- `ldq #$12345678` — no immediate quad mode (`operand must be a 16-bit address`). Load A/X/Y/Z individually, or `LDQ` from a constant in memory.
- `mos8()` forces the *direct* base-page form, not an indirect one — `ldq mos8($12)` assembles to `42 42 a5 12`, i.e. `ldq $12`. It is not a way to get a base-page indirect.

A useful idiom for filling memory fast — broadcast A across all four bytes of Q, then store 4 bytes at once:

```c
asm volatile("tax\n\t" "tay\n\t" "taz\n\t"   // A -> X, Y, Z: Q = vvvvvvvv
             "stq (%[ptr])\n\t"
             "ldz #0"                         // restore the invariant
             :: "a"(val), [ptr] "r"(dst)
             : "x", "y", "p", "memory");
```

## 5. 32-bit flat addressing

`[$nn],Z` reads a **4-byte pointer** from the base page and addresses the 45GS02's true 28-bit address space directly — not the CPU's current 64K view. This reaches any memory without bank switching or DMA, and is often the simplest way to touch far memory from C.

The `[...]` form is encoded by a `$EA` (NOP) prefix on the ordinary indirect opcode.

```asm
; $12..$15 contain $20 $30 $FD $0F  =  $FFD3020 (VIC-IV border colour)
LDA #$06
LDZ #$01
STA [$12],Z      ; writes $FFD3021 — screen colour — via 28-bit address + Z
```

Note that Z *is* a real index here (unlike in Q stores), so this is also the one place where a non-zero Z is doing useful work. Restore it afterwards.

Both byte (`LDA`/`STA`) and quad (`LDQ`/`STQ [$nn]`) forms exist.

## 6. MAP and EOM

`MAP` sets the C65/MEGA65 memory map from A, X, Y, and Z, and **blocks all interrupts — including NMI — until an `EOM` (`NOP`) executes**. The two must be paired, and the instruction after the mapping change must itself be at a mapped, valid address or behaviour is undefined.

Practical consequences when calling `MAP` from inline asm:

- Clobber `"a"`, `"x"`, `"y"`, `"p"` — and remember Z participates, so §2 applies.
- `MAP` sets the I flag; `EOM` clears it. If you want interrupts to stay off afterwards, follow with an explicit `SEI`.
- Never let compiled code run between `MAP` and `EOM` — keep both in the same asm block.
- Don't map away the memory holding the currently-executing code, the imaginary registers, or the soft stack.

## 7. Inline asm: getting values into Z and Q

Since there's no `z` or `q` constraint, route through what does exist.

**Into Z**: load immediately (`ldz #N`) or transfer from A (`taz`).

```c
asm volatile("taz\n\t" "lda [$12],z\n\t" "ldz #0" : "+a"(v) :: "p");
```

**Out of Z**: `tza` into A, then use an `"=a"` output. If A is already spoken for, save it around the transfer — this is the early-clobber case, because the output is written before the input is finished with:

```c
asm volatile("jsr __RDTIM\n\t"
             "pha\n\t"           // save A (seconds)
             "tza\n\t"           // Z -> A
             "ldz #0\n\t"        // restore invariant while A is safe
             "sta %[tenths]\n\t" // write output before restoring A
             "pla"               // restore A
             : "=a"(tod.seconds), "=x"(tod.minutes), "=y"(tod.hours),
               [tenths] "=&r"(tod.tenths)
             : : "p");
```

The `=&r` is load-bearing: without the `&`, the compiler may allocate that output to a register it still needs as an input.

**32-bit values in and out of Q**: don't try to describe Q to the constraint system. Use memory:

```c
uint32_t in = ..., out;
asm volatile("ldq %[i]\n\t"
             "aslq\n\t"
             "stq %[o]\n\t"
             "ldz #0"
             : [o] "=m"(out) : [i] "m"(in)
             : "a", "x", "y", "p");
```

Because Q *is* A/X/Y/Z, any block using Q clobbers all four — list `"a"`, `"x"`, `"y"` and restore Z.

## 8. What the compiler leaves untouched

Compiled code for `-mcpu=mos45gs02` does **not** emit `LDZ`/`TAZ`/`TZA`, `[...],Z` 32-bit indirects, or any Q instruction. Codegen sticks to the 6502/65CE02-level subset.

Two consequences:

- **Z, Q, and flat 28-bit addressing are yours** — no register-allocation conflict, no need to coordinate with the compiler beyond the Z=0 invariant.
- **The compiler won't do it for you.** If you want DMA, Q-width moves, or far memory access, you write it — via inline asm, a `.s` file, or the SDK's C++ helpers (`mega65::dma` in `dma.hpp`, and the `MATH` hardware multiplier; see `commodore.md`).

For bulk memory work, reach for DMAgic before hand-rolled Q loops: it's substantially faster and `dma.hpp` already handles the F018A/F018B list-format difference.
